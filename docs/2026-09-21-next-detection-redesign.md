## 결론부터 — 6장과 7장은 **한 번에** 해야 한다

결과 문서는 둘을 따로 뒀지만, 나눠서 구현하면 6장 작업이 버려진다. 이유는 아래 두 가지다.

### 이유 1 — 6장 규칙은 이미 헤더 시점에 판정 가능하다

6장이 쓰는 입력은 `Sec-Fetch-*`(요청 헤더)와 `Content-Disposition`/`Content-Type`(응답 헤더)뿐이다.
**본문이 필요 없다.** 즉 그 규칙은 `responseheaders` 훅에 그대로 들어갈 수 있는 형태이고,
7장 구조가 6장 규칙의 자연스러운 집이다.

### 이유 2 — 훅을 옮기면 규칙 3(64KB 크기 폴백)이 성립하지 않는다

`responseheaders` 시점에는 본문이 없으므로 `len(flow.response.content)`를 쓸 수 없다.
`Content-Length`로 바꿔야 하는데 chunked 응답에는 그 헤더가 없다. **규칙 3은 다시 써야 한다.**

## ⚠️ 가장 중요한 제약 — 헤더를 흘려보내면 되돌릴 수 없다

`responseheaders`에서 `flow.response.stream = True`로 통과시킨 flow는 **헤더가 이미 브라우저로
나간다.** 그 뒤에 "본문이 커서 역시 다운로드였다"는 걸 알아도 **보류도 차단도 불가능하다.**

이것은 제품 설계 6장의 *"헤더 전송 후에는 차단 응답을 만들 수 없다"*가 판별 로직에 직접 적용되는
자리다. 따라서:

> **판별은 헤더 시점에 내리는 최종 결정이어야 한다. "일단 흘려보내고 나중에 승격"은 불가능하다.**

크기 기반 폴백을 스트리밍 바이트 카운터로 살리려는 접근은 이 제약 때문에 성립하지 않는다.
(카운터 자체는 `oversize_action` 정책 집행에는 여전히 필요하다 — 그건 이미 다운로드로 판정된
flow의 이야기라 별개다.)

## 규칙 3을 어떻게 다시 쓸 것인가 — 선택지 2개

| | 방식 | 놓칠 위험 | 오탐 위험 |
|---|---|---|---|
| **A (권장)** | `Content-Length`가 있을 때만 크기 폴백 적용. chunked면 크기를 무시하고 맥락 신호(`Sec-Fetch` + `Content-Disposition` + MIME)만으로 판정 | chunked로 내려오는 큰 바이너리 중 MIME·헤더 신호가 전부 없는 경우 | 낮음 |
| **B** | 크기 폴백 자체를 폐기. 맥락 신호만으로 판정 | A보다 조금 더 큼 | 가장 낮음 |

**A를 권장한다.** 다만 두 방식 모두 **기존 139건 데이터셋에 소급 적용해서 비교할 수 있다** —
캡처에 `Content-Length` 유무와 크기가 남아 있다면 재측정 없이 표 하나로 결론이 난다. 그걸 먼저
해보고 고르는 편이 낫다.

규칙 3의 "제외 MIME 목록"(`text/html`, `text/css`, `text/javascript`, `application/json`,
`image/*` 등)은 A·B 어느 쪽이든 그대로 유효하다. 139건 중 80건이 이 목록으로 걸러진다.

## 구현 형태

```
responseheaders 훅
  요청 맥락(Sec-Fetch-*) + 응답 헤더로 판정
    다운로드 아님 → flow.response.stream = True   (버퍼링·보류·이벤트 전부 없음)
    다운로드     → 버퍼 유지 (기본값), response 훅으로 진행

response 훅
  보류 → 판정 → 릴리스/403 → 이벤트 emit
```

동시에 처리될 것 (결과 문서 8장 1번, 원인이 코드 순서다):

- **`BLOCKED` 이벤트의 `mime_type`이 403 교체 응답의 `text/plain`으로 기록되는 문제.**
  `flow.response`를 교체하기 **전에** 원본 헤더를 읽어두면 스키마 변경 없이 해결된다.
  차단된 파일이 원래 무엇이었는지는 기록에서 사라지면 안 되는 값이다.
